# GOALS — цель и критерии готовности

## Цель v1
Одной командой развернуть на Debian/Ubuntu прозрачный шлюз для LAN-клиентов:
весь трафик локальной сети идёт через этот шлюз, и он **селективно** маршрутизирует —
только домены/сервисы, заблокированные в РФ, уходят на VPS через VLESS-туннель,
**остальной трафик идёт напрямую через провайдера** (не в туннель).
DPI обходится локально через zapret. Без настройки на клиенте.
Установка идемпотентна и переживает ребут.

### Принцип роутинга (ядро проекта)
- Заблокированное (по списку доменов/IP) → `proxy-mux` (gRPC-туннель на VPS).
- Всё прочее, приватные сети, VPS, Steam, BitTorrent → `direct` (через провайдера).
- Источник истины — routing-правила [config.template.json:214](xray/config.template.json:214).
- Списки заблокированного: [xray/domains/](xray/domains/) (роутинг) и [zapret/domains/](zapret/domains/) (DPI).

## Критерии «готово» (проверяемые)
Каждый критерий проверяется командой или демонстрацией. Источник — healthcheck в [install.sh:493](install.sh:493).

| # | Критерий | Как проверить |
|---|----------|---------------|
| G1 | xray слушает tproxy | `ss -tlnp \| grep ':12345 '` |
| G2 | VLESS-туннель работает | `curl --socks5-hostname 127.0.0.1:1080 https://api.ipify.org` → IP VPS |
| G3 | nfqws запущен | `pgrep -x nfqws` (≥1 процесс) |
| G4 | NFQUEUE правила есть | `iptables -t mangle -L POSTROUTING -n \| grep NFQUEUE` |
| G5 | Переживает ребут | после reboot G1–G4 всё ещё PASS (не сломан iptables-save) |
| G6 | Заблокированное идёт через VPS | с клиента `curl https://api.ipify.org` → IP **VPS** (ipify в списке/через прокси) |
| G7 | Незаблокированное идёт напрямую | с клиента запрос к РФ-ресурсу (напр. `curl https://api.ip.sb` к не-проксируемому) → IP **провайдера**, не VPS |
| G8 | Установка идемпотентна | повторный `install.sh` не ломает работающий шлюз |

### Что нельзя проверить машиной (чек-лист демонстраций)
- D1: Instagram/WhatsApp открываются с клиента (видео грузится).
- D2: YouTube без буферизации.
- D3: Discord voice работает (через discord-tproxy).

## Процесс пополнения списков (постоянный)
Домены и сервисы добавляются **по мере просьб пользователей** — это штатный цикл сопровождения,
не разовая задача. Куда добавлять (источник истины — код):

| Что нужно | Куда добавить | Реф |
|-----------|---------------|-----|
| Сервис должен ходить через VPS (роутинг) | дописать домен или `geosite:X` в любой тематический `*.txt` | [xray/domains/](xray/domains/) |
| ...по IP-подсетям (без домена) | инлайн ip-правило → `proxy-mux` | [config.template.json](xray/config.template.json) (правило Meta/Telegram IP) |
| DPI-обход для сервиса (zapret) | соответствующий `*.txt` | [zapret/domains/](zapret/domains/) |
| Должен ходить напрямую (исключение) | direct-правило (steam-блок) | [config.template.json](xray/config.template.json) |

Роутинг-список генерируется из `xray/domains/*.txt` скриптом
[xray/build-domains.sh](xray/build-domains.sh) при рендере конфига ([install.sh](install.sh)).
Пополнение = дописать строку в маленький тематический .txt (T6, см. [DECISIONS.md](DECISIONS.md)).

После правки .txt — передеплой (`install.sh` перегенерит и перерендерит config.json) или
вручную на машине: правка `/opt/xray/config.json` + `systemctl restart xray`.

### Сознательные отклонения от ТЗ (обсуждены и согласованы с пользователем)
- **8.3 Консолидация групп** — ТЗ предполагало «группа = 1 демон на несколько доменов».
  17-18 июля (до этой вехи) было явно решено обратное: домен = своя очередь/ipset/демон
  (изоляция важнее экономии процессов). 21 июля перепроверили на реальных цифрах (2 ядра,
  1.9ГБ RAM) — узкое место оказалось не в памяти (55МБ на 27 демонов), а в пуле очередей
  (уже почти исчерпан) — пофиксили это (T52), **консолидацию демонов делать не будем**.
- **8.4 "запуск по триггеру трафика"** — не реализован, живой триггер требует отдельного
  слушателя (детектор игнорирует уже-managed домены). Реактивация — раз в сутки на ночном
  проходе. Если это будет ощутимо мешать — отдельная задача.
- ~~UDP везде в ТЗ~~ — **сделано (T57, 2026-07-21)**. Мозг теперь умеет и TCP, и UDP/QUIC.
  Важная находка по пути: UDP/443 у нас САМИХ глобально DROP кроме Meta ("падать на TCP") —
  для НЕ-Meta доменов большинство `quic-no-response` это наш же DROP, не внешний DPI-блок;
  для таких доменов заводится постоянный ACCEPT без десинхронизации (accept-only), а не полный
  zapret-перебор. YouTube/Instagram по-прежнему через старый статичный мультипрофиль (queue 201),
  не через мозг — не трогали.

### Совсем не начато
- **Раздел 2, eBPF-сенсор** — сейчас детектор на **pcap** (gopacket), не eBPF. Пользователь
  выбрал «переписать на eBPF» в вопросе от 20 июля — это большая отдельная задача (замена
  всего механизма захвата трафика), **не начата**.
- **6.2 Game Mode / импорт `.bat`-конфигов** — custom-пресеты (T51) добавляются вручную через
  API (имя+аргументы nfqws), парсинга готовых `.bat`/`.conf` файлов сообщества нет.
- **10, полная схема БД** — таблиц `resources`, `event_log`, `active_demons`, `settings` нет.
  Состояние по-прежнему в JSON (`brain-services.json`, `autoroute.json`, `zapret-services.json`,
  `connections.json`, `recheck.json`). Решение 2026-07-20: мигрировать НЕ будем, пока это не
  стало реальной проблемой (5 файлов — не так уж много, каждый со своей чёткой ролью).
- **11, UI-интеграция** — вкладки Whitelist/Пресеты сделаны (T56, поверх API T48/T49/T51).
  Featured-вкладки (YouTube/Discord/Instagram/Zapret-прочие) и поиск стратегий убраны целиком —
  пользователю больше не нужно было ручное переключение. Единой таблицы «ресурсов» с фильтрами
  всё ещё нет (ТЗ хочет одну таблицу на все домены — сейчас разделы Автообход/Мониторинг каждый
  про своё, но это уже 2 раздела, не 3-4 как раньше).
  Журнала событий (`event_log`) как отдельной сущности нет — есть только сырой лог
  `/var/log/gateway-brain.log` и `journalctl`.
- **4, точные пороги** (TCP: 4 попытки/60с; UDP: 4-5 датаграмм/10с) — детектор использует
  свои калиброванные пороги (`synThreshold=5` без явного окна, `udpThreshold=8`) — их никто
  не подгонял под цифры из ТЗ, просто переиспользовали уже откалиброванные под этот стенд.
- **12, "nftables"** — проект целиком на **iptables**, не nftables (так было до этого ТЗ,
  переписывать весь iptables-стек на nftables ради буквы документа не обсуждали — вероятно,
  не стоит того).

### Честная оценка объёма
Из «совсем не начато» **eBPF-сенсор — на порядок больше работы**, чем всё сделанное в
T48–T55 вместе взятое (замена всего механизма захвата трафика в проде, риск регрессии
детектора). Остальное (UI-таблица ресурсов, event_log, Game Mode/.bat-импорт) — с точки
зрения объёма скорее сравнимо с одной-двумя done-задачами каждое, не месяцы работы.
**Реалистичный порядок, если продолжать:** (1) UI-панели для уже готового бэкенда
(whitelist/presets — почти бесплатно, бэкенд есть) → (2) решить, нужен ли eBPF прямо сейчас
или pcap продолжает устраивать (он РАБОТАЕТ, включая T48-55, которые все на нём построены) →
(3) остальное (Game Mode/.bat, единая таблица ресурсов, event_log) — по мере желания,
не блокирует ничего уже работающего.
