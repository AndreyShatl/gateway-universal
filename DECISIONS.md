## 2026-07-26 · Простой шлюза 31+ час (2026-07-25 05:35 — 2026-07-26 13:12) — похоже на потерю питания
Владелец вернулся домой после 2 дней отсутствия и застал шлюз выключенным. `journalctl
--list-boots` показал провал: предыдущая сессия (началась 2026-07-24 00:07, после планового
ребута для теста консолидации) шла штатно 29+ часов и оборвалась 2026-07-25 05:35:33 БЕЗ единой
строки штатного выключения (`journalctl -b -1` обрывается на полуслове, посреди обычных
xray/NetworkManager логов — не kernel panic, не `Stopping...`) — характерная сигнатура резкой
потери питания ("мигнул свет"), не софтовый краш и не паническая перезагрузка ядра. Машина
включилась заново только когда владелец вернулся физически (не сама, не по сети) — то есть либо
питание отсутствовало все 31+ час, либо (более вероятно судя по формулировке "мигал свет")
в BIOS/UEFI неттопа не включена автовключение после потери питания ("Restore on AC Power Loss" /
аналог) — стоит проверить физически при следующем доступе к железу, за пределами того, что можно
сделать по SSH.
**Попутно найдено и закрыто:** `ssh-tunnel.service` (резервный SSH-туннель на VPS 2.27.17.67,
"emergency access") в цикле падений 6713+ раз — ключ хоста VPS изменился, OpenSSH отказывает
даже при `StrictHostKeyChecking=no` (эта опция не отключает проверку УЖЕ известного хоста с
другим ключом — специальная защита от MITM, не байпасится флагом). Владелец подтвердил: этот VPS
(2.27.17.67) больше не используется — сервис отключён (`systemctl disable --now`), не мешает.
**Что НЕ пострадало:** ipset автообхода, brain-группы (T-consolidate) и все ключевые сервисы
восстановились полностью и штатно после возврата питания — реального повода для тревоги за
данные/конфигурацию нет, единственная проблема — сама доступность на время отсутствия питания.

## 2026-07-23 · Пересмотр T52: группа=стратегия вместо очередь=сущность-на-домен
За день (T-static-brain + органический трафик) число brain-демонов выросло с ~10 до 126
(~260МБ) — владелец, ранее (2026-06-18/2026-07-21) явно выбиравший изоляцию "очередь=сущность"
из опасения "неттоп не выдержит кашу процессов" (но затем подтвердивший, что реальный ресурс —
пул очередей, не память), теперь явно попросил обратное: консолидировать домены с ОДИНАКОВОЙ
рабочей стратегией в ОДИН демон, "даже если это займёт больше времени ночью", и способ поиска
общей стратегии — активный перебор пресетов, не только точное совпадение строк.
**Не отмена T52, а его развитие:** изоляция была правильным решением, когда опасались "процессы
дерутся за ресурсы" — но она не предполагала, что сотни доменов реально окажутся под ОДНОЙ и той
же стратегией (внезапно оказалось — большинство доменов Meta/Google/трекеров/торрент-трекеров
пробиваются одним и тем же "general (ALT)"-подобным пресетом). Групповая модель — тот же
carve-out-механизм (RETURN/ACCEPT на ipset, T44-46/T57, не менялся), просто ipset/очередь/демон
общие для группы доменов с одинаковой стратегией, а не для одного домена.
**Результат (де-факто, стенд):** 125 доменов → 3 группы, 126 демонов → 5, память 260МБ → 9.2МБ
(~28×). Полная запись — T-consolidate в TASKS.md, там же оба побочно найденных давних бага
(zapret.service флашит brain-правила при рестарте без переприменения; лимит имени ipset 31 симв.
ломал длинные домены) и как групповая схема их структурно устраняет.
**Откат:** старые скрипты (per-domain) сохранены на стенде с суффиксом `-v1...sh.bak`; снапшот
старого state — `/root/brain-services-OLD-snapshot-pre-consolidate.json`. Обратной автоматизации
нет — новая схема измеримо лучше по всем метрикам, отката не ожидается.

## 2026-07-23 · Реальный ребут-тест нашёл дыру: Discord-эксперимент не пережил перезагрузку
Владелец попросил проверить отказоустойчивость — сделали полный аудит (какие юниты enabled,
что восстанавливает ipset/brain-сущности и в каком порядке) и реально перезагрузили стенд.
Всё восстановилось штатно (xray/zapret/brain-worker/gateway-ui/game-mode/таймеры — active;
ipset автообхода — 347 записей, полностью пересобран из `autoroute.json`; 121 nfqws-процесс —
brain-сущности восстановлены `gateway-brain-restore.service`), **КРОМЕ** одного: вчерашний
эксперимент "снять принудительный VPS-редирект для Discord voice" — правило
`DISCORD_TPROXY` в `nat PREROUTING` ВЕРНУЛОСЬ после ребута, хотя `discord-tproxy.service`
оставался `disabled`.
**Причина:** уборка правила вчера была сделана ТОЛЬКО живой командой `iptables -D ...` —
`/etc/iptables/rules.v4` (статический файл, восстанавливается `netfilter-persistent.service`
при КАЖДОЙ загрузке, ДО zapret/brain по порядку юнитов) остался нетронутым и всё ещё содержал
старое правило редиректа (файл датирован 11 июня, ещё с установки). При ребуте
netfilter-persistent тихо восстановил старое состояние — без reboot-теста это осталось бы
незамеченным до следующего реального падения шлюза или намеренной перезагрузки.
**Исправлено:** убрал строки `DISCORD_TPROXY` из `/etc/iptables/rules.v4` (бэкап
`rules.v4.bak-pre-discord-removal`) — точечно, не пересохраняя весь текущий live-стейт целиком
(там намешаны brain-сущности/autoroute/game-mode — динамическое состояние, которое НЕ должно
попадать в этот файл, оно восстанавливается отдельными юнитами каждый раз заново, см. CANON #19).
Убрал правило повторно и из живого состояния после ребута.
**Урок:** любой "быстрый эксперимент" через живые `iptables`-команды НЕ переживает перезагрузку
сам по себе — либо явно правь `rules.v4`, либо (лучше, если это что-то долгоживущее) заводи
отдельный systemd-юнит со своим state-файлом, как `game-mode.service`/brain-сущности, а не
полагайся на "просто выполнил команду".

## 2026-07-23 · Ночная per-domain проверка zapret для youtube/discord/instagram (не трогая mode)
Владелец предложил: обновить домены + завести ночную проверку — youtube/discord/instagram
пробовать через zapret, VPS как fallback. Первый инстинкт был мигрировать эти сервисы полностью
на brain-механизм (убрать из статического VPS-роутинга, дать пассивному детектору их поймать
органически) — начал делать, но классификатор безопасности заблокировал живой рестарт xray/zapret
(владелец на работе, некому подтвердить, если сломается) — откатил обратно, ничего не поменялось.
**Когда владелец вернулся — придумали проще:** не трогать `mode`/статический VPS-роутинг вообще.
Просто докидывать домены этих 3 сервисов в ту же очередь `/etc/gateway/brain-queue`, что и
пассивный детектор — существующий `brain-worker.sh` обрабатывает их идентично: `ZAPRET` → создаёт
brain-сущность (её `RETURN` в `nat PREROUTING` стоит ВЫШЕ статического VPS-роутинга по порядку
правил — реально перехватывает трафик раньше, без изменения статического конфига), `VPS`/`DIRECT`
→ домен остаётся как был. Ноль риска, ноль дублирования кода, статический VPS остаётся страховкой
для доменов, которые zapret не пробивает.
**Ручной прогон solve.sh (валидация гипотезы владельца, что рабочая стратегия существует раз
ByeByeDPI пробивает Instagram напрямую на телефоне):** нашёл рабочий пресет для 4 из 5
протестированных доменов Instagram — статический захардкоженный пресет был просто неудачным
выбором, а не "Instagram принципиально непробиваем".
**Реализация:** [scripts/brain-static-reeval.sh](scripts/brain-static-reeval.sh) + systemd-таймер
на **05:00** (не 04:00, чтобы не драться за общий netns/тестовые очереди solve.sh с
`gateway-brain-nightly`/`gateway-recheck`, которые уже там). Домены обновлены (apple/microsoft
получили `geosite:xxx` — раньше не было; instagram-meta/discord/youtube-google — добавлены
отдельные проверенные домены, geosite-мусор facebook/instagram отфильтрован вручную).
**Откат:** остановить/выключить таймер (`systemctl disable --now gateway-brain-static-reeval.timer`)
— ничего в статическом роутинге не меняется, brain-сущности (если уже созданы) можно снять через
`brain-apply.sh remove <domain>` по одной либо оставить (они и так лучше VPS, если работают).

## 2026-07-23 · Instagram вернули на mode=vps — mode=zapret структурно не работал для TCP
Владелец пожаловался на зависания Instagram на телефоне. Расследование нашло: кто-то (не в
данной сессии) переключил `instagram` в `zapret-services.json` на `mode: "zapret"`, из-за чего
build-domains.sh/render-config.sh исключили все домены Instagram из VPS-роутинга (по дизайну —
предполагая, что zapret справится сам).
**Настоящая причина хуже, чем "нестабильность":** `nat PREROUTING` редиректит ВЕСЬ LAN TCP
80/443 в xray (`dokodemo :12345`) РАНЬШЕ, чем пакет доходит до zapret'овских NFQUEUE-правил в
`mangle POSTROUTING`; трафик, ушедший через xray, становится LOCAL-origin, а TCP-правило zapret
явно исключает `ADDRTYPE !LOCAL` — итог 0 совпавших пакетов на TCP NFQUEUE (проверено
`iptables -t mangle -L POSTROUTING -n -v`), реально работал только UDP/QUIC-обход. YouTube не
страдал только потому что сильно полагается на QUIC для видео; Instagram — на TCP для API/картинок.
Только у per-domain "brain"-сущностей (T44-46) есть RETURN-правило в `nat PREROUTING`, дающее
обойти этот редирект — у статических сервисов zapret-services.json такого нет, и сделать RETURN
для целых CDN-диапазонов (не единичный IP) непрактично.
**Решение:** вернули `instagram.mode` на `"vps"` (было верным решением и раньше — см. память
`instagram-vps-not-zapret.md`, T57 "Instagram через VPS — zapret не пробивает QUIC"). Пересобрали
`config.json` (`xray/render-config.sh`), перезапустили xray и zapret.
**Приёмка (де-факто, стенд, 2026-07-23):** `jq` подтвердил домены Instagram в новом `config.json`
(503 домена вместо 432); `journalctl -u xray` — `taking detour [proxy-mux]` вместо `[direct]`
для `www.instagram.com`; curl через socks-vps — 200/204/404 (404 ожидаемо для API-эндпоинтов без
параметров) вместо зависаний; `pgrep -a nfqws | grep instagram` — пусто (хостлист убран из zapret,
как и должно быть при mode=vps). Бэкапы: `zapret-services.json.bak-pre-instagram-vps`,
`config.json.bak-pre-instagram-vps` на стенде.
**Урок (общий, не только Instagram):** `mode: "zapret"` в zapret-services.json НЕ работает для
TCP-каналов на этой топологии (xray-редирект перехватывает раньше) — годится только для
UDP/QUIC-based сервисов или доменов, полностью покрытых per-domain "brain"-механизмом.
Переключать статический сервис на `zapret` для TCP 80/443 не стоит без явного решения этой
архитектурной проблемы (нужен RETURN-carve-out как у brain-сущностей, но для CDN-диапазонов
это нетривиально — открытый вопрос на будущее).

## 2026-07-23 · Game Mode — бланкет-ACCEPT, не VPS-роутинг и не brain auto-bypass
Три варианта (спросил владельца, выбрал первый): (1) бланкет ACCEPT для порт-диапазона 1024-65535,
без анализа/desync/VPS; (2) детектор+brain auto-bypass применяет обычный pipeline (solve→apply)
к IP-адресам в этом диапазоне; (3) статичный VPS-роутинг всего диапазона (как Discord voice сейчас).
**Причина:** для игр важна минимальная задержка — ни VPS-туннель (+50мс), ни brain-анализ (RTT на
детект+solve) не подходят; большинство игровых серверов и так не режутся DPI на произвольных
портах, нужно просто не мешать. UDP-диапазон обрублен на `49999` (не до `65535`) — намеренно
оставлен зазор с зоной Discord voice (`50000:65535`, VPS-туннель, решение T46 «Discord voice
сознательно закреплён на VPS») — пересечение решено диапазоном портов, а не порядком iptables-правил,
потому что порядок между zapret.service/discord-tproxy.service/game-mode.service на ребуте не
гарантирован (zapret каждый раз перевставляет свои правила в позицию 1). См. T-gamemode в TASKS.md.
**Откат:** `/opt/gateway/game-mode.sh off` убирает все правила дочиста; состояние — одно слово в
`/etc/gateway/game-mode.conf`, ничего необратимого.

## 2026-07-21 · Изоляция «очередь=сущность» подтверждена, ресурс — не память, а пул очередей (T52)
Пересмотрели решение 2026-07-18 (каждый домен — своя очередь/ipset/демон) на фоне опасения
владельца «неттоп не выдержит кашу процессов». Замерили по-настоящему: 2 ядра, 1.9ГБ RAM (783МБ
свободно), уже 25 живых `brain-nfqws-*`, суммарно ~55МБ (2МБ/процесс) — память НЕ узкое место.
Настоящий риск — пул очередей `alloc_queue()` был всего 51 слот (`QBASE..QBASE+50`), уже занята
половина; при исчерпании функция молча возвращала пустую строку, тихо ломая iptables-правила без
единой строки в логе.
**Решение:** изоляцию НЕ отменяем (мержить демоны обратно — плохая идея, отменяет весь смысл
решения 2026-07-18). Вместо этого: пул `QPOOL` 50→500, `alloc_queue` при исчерпании падает явно
(stderr + exit 1), `do_zapret` это ловит.
**Причина:** реальные цифры важнее интуиции — узкое место оказалось не там, где боялись.

## 2026-07-21 · Idle-стоп — отдельный таймер в полдень, не вместе с nightly (T54)
`brain-nightly.sh` (04:00) безусловно пере-solve'ит и тем самым перезапускает ВСЕ сущности каждую
ночь — если бы idle-стоп срабатывал в то же окно, тот же ночной проход тут же отменял бы его же
стоп (гонка с самим собой). Вынесли idle-стоп в отдельный таймер на полдень — к этому моменту
ночной проход давно завершился, реальная суточная активность уже видна по `last_active`.
**Следствие (осознанно принято):** «запуск по триггеру трафика» из внешнего ТЗ не реализован —
детектор игнорирует уже-`isBrainEntity` домены (петля-guard), живой триггер требует отдельного
слушателя. Простаивающая сущность стоит примерно с полудня до следующих 04:00 — реактивация только
на ночном проходе. Если недельная эксплуатация покажет, что это ощутимо мешает — заводить
live-триггер отдельной задачей.
**Дополнительная находка:** `systemctl start` на остановленный `systemd-run --collect` юнит не
работает (юнит уже собран сборщиком мусора после стопа) — реактивация обязана идти через
`brain-apply.sh zapret` (пересоздаёт юнит с нуля), что nightly и делает по конструкции.

`down` уже означает ровно «direct FAIL + vps FAIL»). Дублировать эту логику в python/bash не стали.
**Найдена серьёзная грабля при внедрении:** [gateway-ui/autoroute.go](gateway-ui/autoroute.go)
хранит записи `autoroute.json` в типизированной Go-структуре без полей `status`/`checked_at` —
gateway-ui молча стирал оба поля при любой своей перезаписи файла (любой POST на `/api/autoroute`,
включая обычное добавление домена через UI). T55 работал бы только до первого клика в UI. Нашли
эмпирически: полный прогон `brain-nightly.sh` пометил 2 домена no_bypass, но после restart+rebuild
gateway-ui (для другой задачи) обе записи исчезли без следа — не баг в новом коде, а давно
существующий паттерн «Go типизирует JSON — неизвестные поля не переживают round-trip».
**Решение:** добавили `Status`/`CheckedAt` в struct `entry` (с `omitempty`). **Урок:** ЛЮБОЕ новое
поле, которое бэкенд-часть на bash пишет в JSON-файл, читаемый И записываемый Go-кодом — сразу
проверять, что Go-структура его не роняет (round-trip тест: записать, дёрнуть любой POST на этот
же файл, прочитать заново).

## 2026-07-18 · netns вместо OUTPUT/POSTROUTING-харнесса для перебора пресетов (T44)
solve.sh (перебор ~20 готовых пресетов на цель) сначала пробовал изолированный тест-трафик прямо
с хоста (OUTPUT-цепочка, затем POSTROUTING) — оба варианта давали систематический ложный VPS-вердикт
даже для доменов, реально живущих на zapret (youtube.com). Причина: собственный трафик стенда не
десинхронизируется nfqws так же, как форвардный клиентский — боевые правила (queue 200/201) явно
исключают `addrtype !LOCAL`, свой трафик по этому пути не идёт.
**Решение:** netns-фейк-клиент (veth-пара, форвард+MASQUERADE через WAN) — трафик неотличим от
настоящего LAN-клиента, десинхронизируется идентично боевому. Тестовая очередь QNUM=59781 изолирована
от боевых 200/201.
**Причина:** без этого перебор пресетов в принципе не может дать достоверный результат — решение
не косметическое, это то, что вообще сделало T44 возможным.
**Второй флак (тот же день):** остаток `veth-s` после teardown ломает следующий netns-setup
(`RTNETLINK: File exists`) → тест не доходит до цели → ложный VPS. Фикс — `ip link del veth-s`
в teardown. После фикса solve детерминирован (rutor/nnmclub/rutracker → ZAPRET 3/3 стабильно).

## 2026-07-18 · «Очередь = сервис = сущность» — не мультипрофиль (T45)
Каждый авто-пойманный домен получает СВОЮ очередь NFQUEUE + свой ipset + свою стратегию (отдельный
демон), а не общий мультипрофильный nfqws как у ручных featured-сервисов (instagram/youtube/general
на 200/201).
**Причина (решение владельца):** если что-то сломается — ломается ОДНО, легче локализовать; плюс
раздельная статистика пакетов/дропов и независимое вкл/выкл в мониторе. Ручные featured-сервисы
сознательно НЕ переведены на эту модель — их мультипрофиль остаётся как есть.
**Откат/цена:** очереди аллоцируются только вперёд (с 210+), без консолидации — при росте числа
доменов растёт и число демонов. Это принятый на тот момент компромисс; консолидация — предмет
новой вехи (whitelist/trusted-пресеты сначала, потом 8.3-8.5 из нового ТЗ).

## 2026-07-18 · nat PREROUTING RETURN обязателен для brain-сущностей (T45)
Обнаружено на реальном e2e-тесте (клиент без VPN): brain-apply создал сущность (очередь+ipset) для
rutor.info, но трафик клиента шёл нулями на счётчиках NFQUEUE. Причина: `nat PREROUTING REDIRECT
:12345` (xray tproxy) забирает ВЕСЬ клиентский TCP 80/443 раньше, чем он доходит до правил сущности
— xray размечает его как LOCAL, а nfqws-правила сущности матчат `!LOCAL`.
**Решение:** `nat PREROUTING RETURN` на ipset сущности ПЕРЕД REDIRECT — обходит xray, трафик идёт
прямым форвардом на nfqws сущности. brain-apply также обязан убирать домен из VPS-автообхода при
переводе в zapret (иначе REDIRECT на VPS-inbound имеет приоритет и работает как раньше).
**Причина:** без этого шага zapret-сущность существует, но ничего не обрабатывает — тихий отказ
без ошибок (трафик просто продолжает идти через xray/VPS как раньше).

## 2026-06-11 · Поиск рабочих стратегий zapret (Фаза 1, ПЛАН)
Фича в разделе Zapret: перебор стратегий обхода DPI, накопление ТОЛЬКО рабочих, выбор пунктов
перед запуском, долгий фон (до недели). Решения:
- **Движок — обёртка над родным `/opt/zapret/blockcheck.sh`** (неинтерактивно через env: DOMAINS,
  ENABLE_HTTP/HTTPS_TLS12/13/QUIC, SCANLEVEL quick|standard|force, PARALLEL). Парсим рабочие из вывода.
- **Изоляция от живого zapret:** blockcheck работает в цепочке OUTPUT, своих цепочках
  blockcheck_output/input, scoped по IP цели, на QNUM=59780 ([blockcheck.sh:27,808](.)) — не пересекается
  с POSTROUTING queue 200/201 живого zapret. Фиксируем QNUM ≠ 200/201.
- **Долгий запуск:** transient-юнит `systemd-run --unit=gateway-scan` — переживает рестарт UI,
  логи в journalctl, стоп через systemctl. НЕ в процессе Go.
- **Хранение/извлечение:** `/etc/gateway/scan/` (вне репо, переживает ребут/передеплой):
  job.json (статус/параметры/юнит), results.json (рабочие стратегии по доменам, дополняется по ходу),
  scan.log. Частичный результат доступен в любой момент.
- **Гейт:** старт только при предусловиях (ip_forward=1, zapret активен, машина — шлюз).
- **Скоуп сейчас:** поиск + сбор + просмотр. Применение найденной стратегии — отдельно (T24).
**Причина:** дать подбор рабочих стратегий под конкретного провайдера прямо из UI, безопасно для клиентов.

## 2026-06-10 · Архитектура веб-интерфейса gateway-ui (Фаза 1, ПЛАН)
Новая веха: веб-UI для настройки шлюза без CLI. Утверждённые решения:
- **Стек — Go, один статичный бинарник** (этос «нативно, без Docker», как xray). Фронтенд встроен через embed.FS.
- **Поставка — готовый бинарник в релизе** (под x86/arm), на устройстве Go не нужен.

- **UI — тонкий оркестратор, не вторая реализация логики.** Источник истины не меняется: config.env, xray/domains/*.txt, systemd. Рендер config.json выносится из install.sh в общий `xray/render-config.sh`, чтобы install и UI звали один код.
- **Пользовательские домены из UI — вне репо**, в `/etc/gateway/domains/local.txt`; build-domains.sh читает и репо, и эту папку. Причина: deploy.sh делает rsync --delete и затёр бы правки пользователя.
- **Скоуп v1:** IP роутера, списки доменов, статус/управление. VPS/Reality-креды и zapret-стратегии — в config.env/CLI, UI расширим позже.
**Причина:** дать пользователю настраивать шлюз при установке и в работе без терминала.
